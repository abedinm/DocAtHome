Section 1

What is DocAtHome? (The Simple Version)

🏠 One-line explanation you must memorize:

"DocAtHome is a software system where patients can book a doctor or nurse to come to their home, manage their appointments, and pay — all from a desktop app."

🍔 Think of it like Uber Eats — but for healthcare

Instead of ordering food, you're booking a doctor or nurse to come to your house.
Instead of a restaurant, there are doctors and nurses offering their services.
Instead of a delivery tracker, you have an appointment status (Pending → Accepted → Paid).
And an Admin manages the whole platform — like the company behind the app.

🌍 Why does it exist?

In Bangladesh, if you want a doctor at home, you call someone, ask your relatives, or search randomly. There's no proper system. DocAtHome fixes that by making it organized and digital — book online, pay digitally, track everything.

Section 3

How a Booking Works (Step by Step)

If a panel member asks "walk me through the system" — use this flow.

  • 1
    Patient registers in the system and logs in to their dashboard.
  • 2
    Patient clicks "Book Doctor" — picks a doctor, date, time, and reason. The system checks there's no conflict (same doctor, same time).
  • 3
    The booking is created with status "Pending" — the doctor hasn't responded yet.
  • 4
    The doctor logs in, sees the request, and clicks Accept or Reject.
  • 5
    The patient's dashboard updates immediately — they see "Accepted".
  • 6
    The patient selects the accepted appointment and clicks "Pay". They choose Cash, Card, or Bkash. Payment is recorded.
  • 7
    The Admin can see all of this happening in real time from the Admin Dashboard.

💡 Nurse bookings work the same way — just replace "doctor" with "nurse" and "appointment" with "service booking." The nurse also picks a service type like Injection or Wound Care, which has a fixed price.

Section 4

The Database — 7 Tables, Explained Simply

The database is like 7 Excel spreadsheets that store all the data. Each table stores one type of information.

Table NameWhat it storesAnalogy
AdminsAdmin login accountsThe manager's ID card
PatientsPatient profiles, name, phone, medical historyA hospital patient file
DoctorsDoctor info + their specialty + availabilityA doctor's profile card
NursesNurse info + license number + availabilityA nurse's staff record
AppointmentsWhich patient booked which doctor, when, and the current statusA booking confirmation slip
NurseBookingsWhich patient booked which nurse + what serviceA service order form
PaymentsPayment records for both doctor and nurse bookingsA receipt

🔑 The "smart" thing about Payments

Instead of having two payment tables (one for doctors, one for nurses), we use one Payments table with a column called RelatedType that says "Appointment" or "NurseBooking." This saves code and keeps things clean. If the panel asks — this is called a polymorphic table.

Section 5

Technical Terms — What They Mean in Normal Words

The panel might use these words. Here's what they actually mean.

Technical TermWhat it actually means
WinFormsThe type of desktop app — the windows, buttons, and forms you see on screen. Built with C#.
SQL ServerThe database software — where all the data is saved (like a powerful Excel).
ADO.NETThe bridge between the app and the database — how C# talks to SQL Server.
async/awaitWhen the app loads data, it doesn't freeze — you can still move the window. That's async.
Foreign Key (FK)A link between two tables. Like how an Appointment stores a PatientID to know which patient made it.
Primary Key (PK)The unique ID for each row — like a patient's ID number.
3NF (Third Normal Form)A rule for good database design — no repeated/redundant data. Our DB follows this.
BCryptA secure way to store passwords. We use a simpler method for the prototype, but the code is ready to switch.
SMTP / OTPSMTP = email sending. OTP = the 6-digit code sent to email for password reset.
Role-based accessEach user type (Admin, Patient, Doctor, Nurse) has their own screen and permissions.
.NET Framework 4.8The version of Microsoft's software platform the app runs on. Like saying "Android 13" for a phone app.
Parameterized queryA safe way to search the database — prevents hackers from injecting fake commands (SQL injection).
Section 6

Questions the Panel Will Ask — and Safe Answers

These are real questions you might get. Read the answers out loud until you can say them naturally.

Q: What is DocAtHome?
"DocAtHome is a role-based home healthcare management system. Patients can book doctors and nurses for home visits, track their appointment status, and make payments — all from a desktop application. There are four roles: Admin, Patient, Doctor, and Nurse, each with their own dashboard."
Q: What was your contribution to the project?
Pick one area and own it. Options:

Option A (Database): "I worked on the database design — defining the 7 tables, the relationships between them, and ensuring the schema is in Third Normal Form."

Option B (UI/Testing): "I focused on the user interface flow and testing — making sure each role's journey works correctly, forms validate properly, and buttons behave as expected."

Option C (Documentation/Logic): "I handled the business logic planning — defining the booking flow, the appointment status lifecycle, and the payment process."
Q: How does a patient book a doctor?
"The patient logs in and clicks 'Book Doctor.' They select an available doctor from a dropdown — only doctors who have marked themselves available appear. They pick a date, time, and describe their reason. The system checks for conflicts — if the doctor already has a booking at that exact time, the request is blocked. Otherwise it's submitted with status Pending, waiting for the doctor to accept or reject."
Q: How does the payment work?
"Once a doctor or nurse accepts an appointment, the patient can pay from their dashboard. They select the accepted booking and click 'Pay.' A payment form appears with three options: Cash, Card, or Bkash. If they choose Card, a card number field appears and the amount is validated. On confirmation, a payment record is saved to the Payments table and the patient's unpaid bill counter updates."
Q: What is the difference between Appointments and NurseBookings?
"Appointments are for booking a doctor — a general visit with a description of the problem. NurseBookings are for booking a specific nursing service — like an Injection, Wound Care, IV Drip, Physical Therapy, or Elderly Care. Each service has a fixed price defined in the system, from 200 to 400 BDT."
Q: Why did you choose a desktop app?
"Desktop was chosen because it let us focus on the core business logic — the database design, multi-role architecture, and full booking flow — without splitting effort across web servers, APIs, and browser compatibility. WinForms on .NET Framework 4.8 is stable and runs on any Windows machine, which is realistic for a clinic admin workstation. The database is completely independent of the UI, so a web front-end could be added later without changing the schema."
Q: How many tables are in the database?
"Seven tables — Admins, Patients, Doctors, Nurses, Appointments, NurseBookings, and Payments."
Q: Is your database normalized?
"Yes, to Third Normal Form. Each table stores only information about one entity. For example, patient details aren't repeated inside the Appointments table — we only store the PatientID as a foreign key reference. Doctor specialty lives in the Doctors table, not copied into every appointment."
Q: What happens if a doctor rejects an appointment?
"The appointment status changes to Rejected. The patient can see this immediately on their dashboard through the notification banner and the appointment history grid. They can then book again with a different doctor or a different time."
Q: What happens if two patients try to book the same doctor at the same time?
"The system has conflict detection. Before saving any new appointment, it checks if that doctor already has a booking with the same date and time that hasn't been rejected or cancelled. If a conflict is found, the second booking is blocked and the patient is told to pick a different slot."
Q: What would you improve if you had more time?
"Three things. First, proper password hashing with BCrypt — currently it's a prototype stub, but the code is structured so it's literally a two-line change. Second, email notifications when a doctor accepts or rejects — the email infrastructure is already built for OTP, so it's straightforward to extend. Third, a web or mobile front-end that connects to the same database through an API, so patients can book from their phone."
Section 7

🆘 Lifelines — What to Say When You Don't Know

You WILL get a question you don't know. Here's how to handle it without panicking.

🎯
Redirect to something you know "That's related to [part you know] — in our system, [explain what you know]. The specific implementation of [part you don't know] was handled in the [form/database/logic] layer."
🤝
Pass to a groupmate naturally "I can give you the high-level answer — [say what you know] — and [groupmate name] can go deeper on the implementation."
🧱
Answer with the design principle, not the code "The design decision there was to [keep it simple / avoid duplication / make it extensible]. In practice that means [explain what it does in plain English]."
🛡️
The honest pivot (works every time) "Honestly, I'd want to double-check the exact implementation before giving you a wrong answer — but what I can tell you confidently is [something true about the system]."
❌ NEVER say these things:
"I don't know anything about this project." · "I didn't work on that part." · "This isn't my part." · Just going silent and staring at the panel.

⚠️ If the panel asks you to do something live on the app — like change a button color or add a column — just say: "Sure. That would be done in Theme.cs since it centralizes all the visual styles — changing one line there updates every button in every form."
